# Performance testing when background cleanup is uncertain

Public-source research, checked 2026-11-04. This page adds an evidence-handling procedure to the existing [performance research](https://github.com/Herbertofury/TD1-Occult-Hybrid-Apex/wiki/Performance-Research) and [simulation research](https://github.com/Herbertofury/TD1-Occult-Hybrid-Apex/wiki/Simulation-Performance-Research-2026%E2%80%9011). The live wiki was checked at `50de549758f5af56de26e63deaf4757ee9b53757`; existing matched-scenario, semantic-marker and trace-loss guidance is not replaced. This file is repository documentation, not a live wiki edit.

**Recommendation:** continue already-authorized gameplay correctness work, while labeling timing evidence separately. An uncertain helper shutdown is an uncertainty to record, not permission to inspect restricted process metadata, terminate other work, restart the computer, or start a second profiler.

## 1. Separate useful results from an isolated performance claim

These are proposed project reporting rules, not a claim that any current helper is still running:

- **Functional result:** record the actual outcome of the existing test, for example correct form selection, thumbnail identity, favorites interaction, appearance preservation or save/reload behavior. Include build/scenario and relevant evidence. Such an observation remains useful with background state marked unknown. A timing-dependent failure remains an observed failure with cause unresolved.
- **Diagnostic timing:** retain already-authorized measurements and raw evidence, but mark background cleanup unknown. State the measured outcome under those conditions; do not attribute the difference to Apex or treat it as an uncontaminated baseline.
- **Comparative timing:** resume an isolated improvement claim only after both baseline and candidate have matched, documented background conditions and valid captures. Recollect both sides if the condition changed between them. A later cleanup receipt does not automatically establish the state during an earlier capture.

Microsoft recommends minimizing test variables, controlling background apps and repeating runs. Here, when stopping background work is unauthorized or would interrupt active work, the appropriate adaptation is to limit the claim rather than change the machine. [Windows performance measurement guidance](https://learn.microsoft.com/en-us/windows/apps/develop/performance/planning-measuring-performance#test-and-measure-against-performance-goals).

## 2. What does and does not establish cleanup

A trusted, time-stamped completion record from the already-owned workload can establish what that record actually covers. Parent-process exit alone does not prove that child work ended: [Windows explicitly does not terminate child processes when their parent terminates](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process). A stopped CSV, a missing progress message, a quiet-looking scene or elapsed time is not a whole-workload completion receipt.

If no permitted evidence settles the question, keep the state **unknown**. Do not use a different process tool, trace or API to recover metadata that was denied. No process enumeration, WMI/CIM queries, process killing, priority/affinity changes, security changes, reboot or agent interruption is prescribed by this procedure.

Already-authorized aggregate telemetry can describe pressure, but cannot identify or exclude a particular helper. For example, [GetSystemTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getsystemtimes) reports aggregate user/kernel/idle time; kernel time includes idle, and machines above 64 processors have a processor-group limitation. These totals do not measure GPU/disk pressure or prove helper absence. No new collection is required to continue functional testing. [Windows CPU guidance](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis#processor-power-management) also explains power/throttle states: similar utilization alone does not establish equal effective CPU frequency. Do not invent a universal “below X% means clean” threshold.

## 3. PresentMon controls that can otherwise leave uncertainty

The following facts are pinned to official **v2.6.0**, commit `e13fce6acdb55a808fd8318175a56863e532d95f`, not assumed for every installed executable. They are considerations for a separately authorized, owned capture, not instructions to launch one during other active tests.

1. **Recording stopped is not collector stopped.** `--timed` stops recording; `--terminate_after_timed` additionally requests exit. [Timer handler, lines 183–188](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/MainThread.cpp#L183-L188). `--delay` only delays recording: the [architecture states that ETW collection and analysis continue independently of CSV recording](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/PresentMon.hpp#L8-L27). Neither flag verifies that an older helper or its children ended.
2. **Keep capture ownership explicit.** A unique `--session_name` avoids replacing another session, but does not justify adding concurrent capture overhead. Without `--stop_existing_session`, a name collision exits with error 6; the destructive alternate branch stops the named session. Do not use `--stop_existing_session` or `--terminate_existing_session` on an uncertain owner. [Collision handling, lines 327–357](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/MainThread.cpp#L327-L357); [documented options](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/README-ConsoleApplication.md#L46-L55).
3. **No invented non-elevation switch.** This parser defaults `mTryToElevate` to false and supports `--restart_as_admin`; `--dont_restart_as_admin` is not a recognized v2.6.0 option. Omitting the restart option prevents that relaunch, but is not a permission-neutral-startup guarantee: the [live path still attempts EnableDebugPrivilege](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/MainThread.cpp#L255-L276). Do not add elevation or launch a capture whose access is not authorized. [Defaults](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/CommandLine.cpp#L377-L414), [recognized execution options and rejection](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/CommandLine.cpp#L463-L495).
4. **Retain the normal completion evidence.** On normal shutdown the main thread stops the session, joins consumption/output, and reports lost ETW buffers/events and overflowed presents. Preserve those diagnostics with the CSV. A CSV file by itself does not prove this shutdown path completed. [Shutdown sequence, lines 440–458](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/MainThread.cpp#L440-L458).

### A target-process filter is not a privacy or workload-isolation boundary

`--process_name` and `--process_id` select reported/tracked frames; they neither suspend competitors nor guarantee collection of only that process's metadata.

- The live output path [opens a process and queries its image name](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/OutputThread.cpp#L294-L319); [the call precedes output target selection](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/OutputThread.cpp#L340-L353).
- The consumer [decodes process ID and image-name events](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentData/PresentMonTraceConsumer.cpp#L2834-L2859), and [PID filtering retains DWM](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentData/PresentMonTraceConsumer.cpp#L3609-L3618).
- The provider filter shown here is [an event-ID filter](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentData/PresentMonTraceSession.cpp#L111-L129), not a guarantee of target-PID-only metadata acquisition.

Therefore a known game PID/name does not authorize a capture that would collect denied metadata. If permitted collection scope is insufficient, use only existing authorized CSV/ETL evidence and existing gameplay observations. `--etl_file` can analyze an already-authorized ETL instead of live processes, but replay cannot undo the original background contention, missing events or original collection scope. See [console target options](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/README-ConsoleApplication.md#L10-L17).

Also, replay without an ETW-loss warning does not certify lossless original collection. The [loss-count query is inside the live session-handle branch](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentData/PresentMonTraceSession.cpp#L598-L614); retain the original diagnostics. [ETL replay uses current recording state](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/PresentMon/OutputThread.cpp#L42-L58), so do not treat wall-clock delay/timed switches as historical trace-time cropping. Slice authorized output using its recorded timestamps instead.

[CPU Busy/Wait calculations](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/IntelPresentMon/CommonUtilities/mc/MetricsCalculatorCpuGpu.cpp#L14-L54) use frame/presentation boundaries. They are not whole-system utilization or attribution to a particular helper.

## 4. A future matched experiment, without interrupting current work

This is an experiment-design proposal for the existing test owner's next appropriate window:

1. Prespecify the exact scenario, semantic start/end, cold-versus-warm state, capture settings, warm-up procedure, repetition count and exclusion rules. Keep excluded runs and reasons. Do not remove a run simply because its stall is large or inconvenient.
2. Repeat the unchanged build first using the same scenario. Large run-to-run drift is evidence that a proposed small gain cannot yet be separated from variation; stable repeats still do not prove helper absence.
3. Once background conditions are sufficiently known and matched, compare baseline/candidate within the same scenario/session blocks. Balance their order and randomize where the approved workflow permits; do not run all baselines first and all candidates after a background task happens to finish. This adapts [NIST's blocking/randomization guidance](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm). Randomization reduces nuisance bias; it cannot certify unknown cleanup or rescue a systematically confounded comparison.
4. Treat repeated scenario runs, not thousands of adjacent frames, as the replication unit for a simple comparison. Report per-run summaries and their spread. Do not calculate a narrow independent-sample uncertainty from correlated frames without a valid time-series method. [NIST on autocorrelated measurement uncertainty](https://www.nist.gov/programs-projects/uncertainty-analysis-autocorrelated-measurement-data).
5. Keep functional acceptance independent: a faster incomplete operation is not an improvement. Keep cold loading, first CAS use, warm scrolling and Live-mode scenarios separate as already required by the project.

## Minimal evidence record

For each run, retain: scenario and build identity; observed functional result; timing eligibility and reason; helper/background state (`known`, `unknown`, or an explicitly controlled load); completion evidence scope and timestamp if available; capture identity/options and normal-exit/loss evidence if available; cold/warm state; raw artifact links; and any exclusion reason. Unknown fields remain unknown.

No machine inspection, capture, benchmark or cleanup was performed in this research pass. No speedup is claimed. PresentMon's [MIT license](https://github.com/GameTechDev/PresentMon/blob/e13fce6acdb55a808fd8318175a56863e532d95f/LICENSE.txt) allows adaptation with its notices retained; source availability does not grant permission to inspect a user's processes. Microsoft and NIST references support the measurement reasoning, not a blanket authorization to change the test system.
